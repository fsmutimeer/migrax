<h2 class="mx-section-title mx-reveal">See it in 30 seconds</h2>
<p class="mx-section-lead mx-reveal">Change an entity, and Migrax writes the SQL and the script that undoes it.</p>

=== "Add a column"

    <div class="grid mx-example" markdown>

    ```diff title="Customer.java"
       @Column(nullable = false, length = 100)
       String name;
    +
    +  @Column(length = 30)
    +  String phone;
     }
    ```

    ```sql title="0002_add_customers_phone.sql"
    ALTER TABLE customers ADD COLUMN phone varchar(30);
    ```

    ```sql title="rollback/0002_add_customers_phone.sql"
    -- Note: deletes data written to customers.phone since the migration ran.
    ALTER TABLE customers DROP COLUMN phone;
    ```

    </div>

    The new column, and a rollback script that says which data undoing it would delete.
    { .mx-centered }

=== "Rename a column"

    <div class="grid mx-example" markdown>

    ```diff title="Customer.java"
    -  @Column(nullable = false, length = 100)
    -  String name;
    +  @Column(name = "full_name", nullable = false, length = 100)
    +  String fullName;
    ```

    ```sql title="0003_rename_customers_name.sql"
    ALTER TABLE customers RENAME COLUMN name TO full_name;
    ```

    ```sql title="rollback/0003_rename_customers_name.sql"
    ALTER TABLE customers RENAME COLUMN full_name TO name;
    ```

    </div>

    A dropped column next to a new one looks like a rename. Migrax asks, and renames it so the
    data stays; in CI it stops and tells you to pass `--rename`.
    { .mx-centered }

=== "New table"

    <div class="grid mx-example" markdown>

    ```java title="PurchaseOrder.java"
    @Entity
    @Table(name = "orders")
    public class PurchaseOrder {
      @Id
      @GeneratedValue(strategy = GenerationType.IDENTITY)
      Long id;

      @ManyToOne(optional = false)
      Customer customer;

      @Column(nullable = false, precision = 12, scale = 2)
      BigDecimal total;
    }
    ```

    ```sql title="0004_create_orders.sql"
    CREATE TABLE orders (customer_id bigint NOT NULL, id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL, total numeric(12,2) NOT NULL, CONSTRAINT orders_pkey PRIMARY KEY (id));
    ALTER TABLE orders ADD CONSTRAINT fk_orders_customer_id_54d4cc52 FOREIGN KEY (customer_id) REFERENCES customers (id);
    ```

    ```sql title="rollback/0004_create_orders.sql"
    -- Note: deletes data written to orders since the migration ran.
    ALTER TABLE orders DROP CONSTRAINT fk_orders_customer_id_54d4cc52;
    DROP TABLE orders;
    ```

    </div>

    Types and keys come from Hibernate's own mapping, so they match what Hibernate expects;
    unnamed constraints get readable names.
    { .mx-centered }

=== "Remove a column"

    <div class="grid mx-example" markdown>

    ```diff title="Customer.java"
       @Column(name = "full_name", nullable = false, length = 100)
       String fullName;
    -
    -  @Column(length = 30)
    -  String phone;
     }
    ```

    ```console
    $ migrax generate
    1 change(s) for postgresql:
      1. drop column customers.phone  [DESTRUCTIVE]
         ALTER TABLE customers DROP COLUMN phone;
    error[MXE108]: 1 destructive change(s) detected (marked [DESTRUCTIVE] above).
    ```

    ```sql title="rollback/0005_remove_customers_phone.sql"
    -- WARNING: restores the structure of customers.phone but not its data.
    ALTER TABLE customers ADD COLUMN phone varchar(30);
    ```

    </div>

    Nothing is dropped until you say `--allow-destructive`, and the rollback script warns that
    it can't bring the data back.
    { .mx-centered }

<h2 class="mx-section-title mx-reveal">Why teams use Migrax</h2>
<p class="mx-section-lead mx-reveal">Everything a migration needs, checked before it reaches production.</p>

<div class="grid cards mx-features" markdown>

-   :material-auto-fix:{ .lg .middle } __Migrations written for you__

    ---

    Change an entity, run `migrax generate`. Tables, columns, keys, indexes, join tables,
    element collections, sequences and inheritance come out exactly as your Hibernate,
    EclipseLink or OpenJPA maps them.

-   :material-shield-check:{ .lg .middle } __Checked before production__

    ---

    Every migration is linted for statements that lock big tables, fail on existing rows or
    break running instances. `migrax verify` checks the result against your mapping, and
    Hibernate validates it itself.

-   :material-undo-variant:{ .lg .middle } __Rollback included__

    ---

    Each generated migration comes with a rollback script, and `verify` tests every one of
    them: roll back, apply again, same schema.

-   :material-account-question:{ .lg .middle } __Asks before it loses data__

    ---

    A dropped column that looks renamed? Migrax asks, and renames it so the data stays.
    Drops only happen when you say `--allow-destructive`.

-   :material-radar:{ .lg .middle } __Catches manual changes__

    ---

    `migrax drift` compares the live database with what your migrations produce and lists
    every difference, including columns someone made narrower.

-   :material-cog-outline:{ .lg .middle } __Zero setup__

    ---

    Run it in your service folder. It compiles the project, finds the dependencies and reads
    the database settings from your application configuration.

</div>

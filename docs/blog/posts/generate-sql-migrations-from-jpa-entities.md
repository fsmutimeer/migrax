# Generate SQL migrations from your JPA entities

Your JPA entities already describe the schema you want. Writing the same change again by hand
as SQL is slow and easy to get wrong. Migrax compares your entities with the last state you
committed and writes the SQL migration for you, along with a rollback script. You review the
SQL, commit it, and apply it.

This article walks through that loop on a small project: create the first tables, add a
column, and rename one without losing data.

<!-- more -->

!!! info "Tested with"

    Migrax 0.16.0, Hibernate 6.6.13, PostgreSQL 17. Every output below was copied from a real
    run.

## The project

Two entities, a customer and an order:

```java
@Entity
@Table(name = "customers")
public class Customer {
  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  Long id;

  @Column(nullable = false, unique = true, length = 150)
  String email;

  @Column(nullable = false, length = 100)
  String name;
}

@Entity
@Table(name = "orders")
public class PurchaseOrder {
  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  Long id;

  @ManyToOne(optional = false)
  Customer customer;

  @Column(nullable = false, precision = 12, scale = 2)
  BigDecimal total;

  Instant createdAt;
}
```

Migrax needs to know where the database is. In `src/main/resources/application.properties`:

```properties
migrax.url=jdbc:postgresql://localhost:5432/shop
migrax.user=shop
migrax.password=shop
```

A Spring Boot, Quarkus, Micronaut or Helidon project can skip this: Migrax reads the
framework's own data source settings.

[Install Migrax](../../getting-started/installation.md), then run `migrax init` and
`migrax doctor` in the project folder. `init` creates the migration folder; `doctor` checks
that the project compiles, finds the entities and reaches the database.

## The first migration

```console
$ migrax generate
No snapshot yet: using the current database schema as the baseline.
Created src/main/resources/db/migration/0001_initial.sql:
  - create table customers
  - create table orders
  - add foreign key fk_orders_customer_id_54d4cc52 on orders
Rollback script written to src/main/resources/db/migration/rollback.
Review the SQL, then run 'migrax migrate'.
```

Migrax reads the entities through Hibernate's own mapping, so the SQL matches what Hibernate
expects, column types and constraint names included:

```sql title="db/migration/0001_initial.sql"
-- Generated by Migrax 0.16.0 for postgresql

CREATE TABLE customers (email varchar(150) NOT NULL, id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL, name varchar(100) NOT NULL, CONSTRAINT customers_pkey PRIMARY KEY (id), CONSTRAINT uk_customers_email UNIQUE (email));
CREATE TABLE orders (createdAt timestamp(6) with time zone, customer_id bigint NOT NULL, id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL, total numeric(12,2) NOT NULL, CONSTRAINT orders_pkey PRIMARY KEY (id));
ALTER TABLE orders ADD CONSTRAINT fk_orders_customer_id_54d4cc52 FOREIGN KEY (customer_id) REFERENCES customers (id);
```

Next to it is the rollback script. It says which data a rollback would delete:

```sql title="db/migration/rollback/0001_initial.sql"
-- Generated by Migrax 0.16.0 for postgresql
-- Rollback for 0001_initial.sql. 'migrax rollback' runs it.
-- Note: deletes data written to customers since the migration ran.
-- Note: deletes data written to orders since the migration ran.

ALTER TABLE orders DROP CONSTRAINT fk_orders_customer_id_54d4cc52;
DROP TABLE customers;
DROP TABLE orders;
```

Both are plain SQL files. Read them, change them if you want, and apply them:

```console
$ migrax migrate
Applying migration '0001_initial.sql'...
Successfully applied migration '0001_initial.sql'.
Applied 1 migration(s); 1 total in src/main/resources/db/migration.
```

Migrax also wrote `.migrax/snapshot.json`: the schema your entities describe right now.
Commit it with the migration files. The next `generate` compares against it, so it doesn't
need a database to work out what changed.

## Adding a column

Add a field to `Customer`:

```java
  @Column(length = 30)
  String phone;
```

```console
$ migrax generate
Created src/main/resources/db/migration/0002_add_customers_phone.sql:
  - add column customers.phone
Rollback script written to src/main/resources/db/migration/rollback.
Review the SQL, then run 'migrax migrate'.
```

```sql title="db/migration/0002_add_customers_phone.sql"
ALTER TABLE customers ADD COLUMN phone varchar(30);
```

The file name describes the change. The rollback script is
`ALTER TABLE customers DROP COLUMN phone;`.

## Renaming a column without losing data

Renames are where generated migrations usually go wrong. If `name` becomes `fullName`, a
simple comparison sees one column disappear and another appear, then drops the old column
and all its data with it.

Change the field:

```java
  @Column(name = "full_name", nullable = false, length = 100)
  String fullName;
```

In a terminal, `migrax generate` asks whether `customers.name` was renamed to
`customers.full_name`. In a script or a CI job, where nobody can answer, it refuses to
write the migration and explains what to do:

```console
$ migrax generate
Possible rename: customers.name to customers.full_name. To keep the data, rerun with --rename customers.name=full_name.
2 change(s) for postgresql:
  1. drop column customers.name  [DESTRUCTIVE]
     ALTER TABLE customers DROP COLUMN name;
  2. add column customers.full_name
     ALTER TABLE customers ADD COLUMN full_name varchar(100) NOT NULL;
error[MXE108]: 1 destructive change(s) detected (marked [DESTRUCTIVE] above).
Review them, then run 'migrax generate --allow-destructive'. If a column or table was renamed, pass --rename table.old=new or --rename-table old=new instead.
```

Nothing is dropped unless you ask for it. Following the hint:

```console
$ migrax generate --rename customers.name=full_name
Created src/main/resources/db/migration/0003_rename_customers_name.sql:
  - rename column customers.name to full_name
Rollback script written to src/main/resources/db/migration/rollback.
src/main/resources/db/migration/0003_rename_customers_name.sql, statement 1: warning MX008
  ALTER TABLE customers RENAME COLUMN name TO full_name
  Application instances still running the old code use the old name and will fail.
  Fix: Rename in steps: add the new name, write to both, switch reads, then remove the old name ('migrax generate --zero-downtime' does this). Or deploy during a maintenance window.
Review the SQL, then run 'migrax migrate'.
```

The migration is now a single `RENAME COLUMN`, and the data stays. Migrax also checked the
new SQL and warned about something easy to miss: during a rolling deployment, the instances
still running the old code look for `name` and fail. For that case,
`generate --zero-downtime` splits the rename into safe steps (a later article covers this).

## Applying and undoing

```console
$ migrax migrate
Applying migration '0003_rename_customers_name.sql'...
Successfully applied migration '0003_rename_customers_name.sql'.
Applied 1 migration(s); 3 total in src/main/resources/db/migration.

$ migrax status
Migrations in src/main/resources/db/migration for jdbc:postgresql://localhost:5432/shop
  [X] 0001_initial.sql                applied 2026-10-20 21:31:26
  [X] 0002_add_customers_phone.sql    applied 2026-10-20 21:31:42
  [X] 0003_rename_customers_name.sql  applied 2026-10-20 21:31:57
3 applied.
```

If something is wrong, `migrax rollback --yes` runs the newest rollback script. Here that
renames `full_name` back to `name`, so the data is still there. Without `--yes`, Migrax only
shows what it would undo and asks you to back up the database first.

## Keeping entities and migrations in sync

Someone will eventually change an entity and forget to generate the migration. `migrax
check` catches that without a database, so it fits in CI:

```console
$ migrax check
2 entity change(s) have no migration:
  - drop column customers.name
  - add column customers.full_name
Run 'migrax generate' and commit the result.
```

It exits with code 2 when a migration is missing and 0 when everything matches:

```console
$ migrax check
OK: entities match the snapshot.
```

## Summary

- Change an entity, run `migrax generate`, read the SQL, commit, run `migrax migrate`.
- Every migration comes with a rollback script that says what data it would delete.
- Destructive changes are never written silently; renames keep the data.
- New SQL is checked for problems such as renames that break a rolling deployment.
- `migrax check` in CI catches entity changes that have no migration.
